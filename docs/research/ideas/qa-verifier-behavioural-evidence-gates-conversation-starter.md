## The problem, in one paragraph

A GREEN currently means "it type-checks," not "it works." AutoBuild's oracle is (spec/Gherkin) + (tests) + (Coach code review), and a stub returning plausibly-shaped data passes all three — Player and Coach share that oracle, so the Coach cannot catch what the tests miss. This is caught in the wild: `fs-01-coach-false-approval-partial-run` (FEAT-MEM-04) — a green Coach, 7/7 SUCCESS, hid a real `app.py` lifespan/DI regression, found only by an independent full-suite run. **This feature is the fix for that class.** Full root-cause and the connection to the meta-harness eval corpus are in the shared overview.

---

## The core design principle

**The fine-tune is not what catches stubs — the independent evidence is.** The QA Verifier is the model behind `--coach-model`; the LLM stays the judge, deterministic Python collects the evidence. The value is an oracle **the Player did not author, exercising real behaviour end-to-end.** The fine-tuned Coach makes the judge better at *reading and generalising over* that evidence — it is downstream of the evidence, not a substitute for it. Hence Phase 0 (deterministic gates, no fine-tune) ships first and alone closes the `fs-01` class.

## Phased scope (for `/feature-plan` to turn into task waves)

**Phase 0 — deterministic evidence gates (no fine-tune):**
- **Anti-stub AST scan** — flag function bodies that are only `pass` / `...` / `raise NotImplementedError` / a bare `return None|[]|{}` with no other statements, or carry TODO/FIXME/stub markers.
- **Coverage / reachability gate** — run the suite under coverage; flag public functions in the feature's changed files with 0% real execution, or whose only covering test never asserts on real output.
- **Behavioural acceptance oracle** — a round-trip against the live dependency the Player didn't write. For fleet-memory this **is** FEAT-MEM-05 (parity harness, built, not yet run); generalise the hook so any feature can declare one.
- **Evidence bundle** — the format the gates emit and the Coach consumes via `--coach-model`, extending `{decision, score, issues, criteria_met, quality_assessment}` with a `behavioural_evidence` block.

**Phase 1 — fine-tuned judge:**
- Build the small golden calibration set (Opus via Max), fine-tune Gemma 4 26B-A4B on reading the evidence bundle and emitting the GREEN/RED verdict, generalising stub detection beyond the hand-specified gates.

## What needs attention in this session (open questions for `/feature-spec`)

1. **Evidence bundle contract** — exact schema the deterministic collectors emit. Precise shape of the `behavioural_evidence` block; how the Coach references specific gate failures in its `issues` array.
2. **"Public surface" definition** — which changed-file set defines the feature's public surface for the AST and coverage gates: the `.guardkit/features/*.yaml` task file, git diff, or both?
3. **Oracle declaration** — how does a feature *declare* its behavioural oracle? Convention (`tests/acceptance/{feature}_roundtrip.py`) or a manifest field? fleet-memory → FEAT-MEM-05; generalise the hook.
4. **Missing-vs-failed oracle policy** — verdict when a behavioural oracle *fails* (hard RED) vs when one is *absent*. Don't let "no acceptance test" silently pass — but decide whether absence is a RED, a WARN, or a gate on the feature spec requiring one.
5. **COACHGATHER01 interaction** — four guards currently compensate for Phase-A gather degrading to B-min 100% of the time. Does the evidence-gate work shrink that compensation surface enough to fix or retire gather?
6. **Seam discipline** — this feature changes what `--coach-model` emits (the `behavioural_evidence` block). That is the frozen seam `forge` consumes (shared overview). Confirm the schema change is additive and versioned so the UBS adapter keeps parsing — the one place this guardkit work has a cross-repo consequence, and it must go through the seam contract, not a `forge` edit.
